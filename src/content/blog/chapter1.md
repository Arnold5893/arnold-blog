### 本章回顾&总结
Agent = llm + 上下文 + 工具，llm是决策核心，上下文决定llm能看到什么，工具决定llm能做什么，在模型固定时，重新定义或扩展上下文（观察空间）和工具（动作空间）能有效提升Agent的整体能力（参考openclaw），注意这种扩展按需进行，且需要考虑合规性

上下文由==静态前缀==（system prompt 和 工具schema）和 ==动态轨迹==（**用户消息** + **assistant消息**（**模型思考内容**reasoning_content 和 **模型的工具调用指令** tool_calls）+ **工具调用结果**）构成

消融实验表明，去掉上下文的任一部分都可能导致Agent无法正确完成任务；在实验中（我用的doubao模型），去掉“模型过去的思考内容”后仍能正确完成任务，因为所用模型有thinking能力，可以根据用户问题、工具调用结果等重新思考和规划；no_tool_result导致模型调用工具却始终拿不到结果，为了回复用户只好瞎编；no_history即去掉动态轨迹，仅向模型发送系统提示词和当前任务，不保留任何ReAct步骤。因此模型会遗忘此前所有操作步骤，易重复调用工具

ReAct循环——让Agent先思考再行动：思考-行动-观察，模型先根据用户输入判断是否需要调用工具，如果不需要直接根据问题输出答案，如需要，调用工具得到结果，结合结果再次思考是否需要调用工具，如此循环直到不需要调用工具，根据工具结果回答用户问题

工具调用分为内置工具（由模型厂商提供和维护）和自定义工具（自己写的工具/函数或调用第三方api），内置工具的工具schema从厂商**服务器动态获取**或者写一段**工具调用的极简声明**即可（根据服务商而定），不需要自己写；自定义工具的工具schema需要自己写

==内置工具会锁定厂商，而自定义工具的灵活度高，不受厂商限制==，具体的选择要考虑效率、灵活度、成本要求等

Harness里那些给模型能力短板打补丁的部分，会随着模型变强被模型内化（参考思考题10的回答），或者是服务商提供的功能变多，部分代码从客户端移到服务端

#### 回答本章前我的疑问：
1. Agent和Harness的关系：Agent = Model + Harness
Harness是Agent之内、llm之外的部分，包括上下文管理、工具管理、循环控制、约束/安全、验证与纠错、记录与证据
2. Harness和ReAct循环的关系：ReAct循环是Harness的组成部分，Harness驱动ReAct循环、决定循环何时停
#### 思考题（附我的思考和ai参考答案）：
1. 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具—— 你会选哪个？在什么条件下你的选择会改变？

对于日常任务：当前的模型能力已经足够强，我倾向于选择更丰富的上下文，尤其是跨对话的记忆能力更强，这样Agent更像我的左膀右臂hhh，可以高效地帮我处理各种事宜
也许遇到更复杂的、当前模型解决不了的问题时会选择更强模型

2. ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

像精简上下文那样，当读取量达到设定的最大值时，用一个llm专门负责提炼此前的核心内容，压缩读取量

ai方案：
- KV Cache / Prompt Caching前缀缓存
- 工具调用结果剪裁：只保留关键字段，总内容存到文件、上下文只留引用/路径
- 滑动窗口+摘要混合：近期消息保留原文，远期消息压缩

3. “模型即 Agent”范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

随着模型越来越强，可做的事情更多，不免出现会出现高风险操作，Harness用于规范模型的行为，并且能让模型更好地了解上下文，以给出更高质量的回复/任务完成质量更高

4. 消融实验中“工具结果反馈”的缺失导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？

no_history也会导致无限循环——==ai说这仍属于题目已给的"信息缺失"范畴==

ai答案：
- 工具调用报错但错误信息无区分度（模型反复尝试调用同一工具）
- 任务目标本身不可能完成
- 幻觉出不存在的工具/参数，被拒绝后反复尝试

检测：判断“历史消息、工具调用结果是否为None或空字符串”，如果是，终止循环退出并返回一段报错信息（仅能解决信息缺失问题）

终止机制：设置最大可迭代次数

ai补充：**重复动作检测**(连续 N 次调用相同工具+相同参数则中断)、**进度检测**(状态哈希无变化)

5. 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这 三个维度进行分析，并思考它的架构设计是否合理

claude：根据用户输入思考都需要做什么，是否需要调用工具，并根据工具调用结果思考和回答问题；以“讨论某项目的py文件为例”，我对某个项目文件的代码存在疑问，claude判断需要先获取这个文件的具体内容，然后它搜索阅读这个项目文件，定位到具体代码，并根据其知识回答我的疑问；

ai答案：感知：claude能接收和读取文本、图片、文件；行动：文件读写、代码执行、网络搜索等工具调用，**动作空间开放式**；策略：ReAct循环——思考-调用工具-根据结果继续思考-回答

6. 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

初期先搭建工作流模式，工作流模式承担**常用任务、确定性流程**（航班查询、选座、支付、改签、退票），
后期逐渐加入自主Agent模式，用于处理那些比较灵活的问题（但要设置安全机制）

7. 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下 变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

不能因为一个工具在大部分情况下都是低风险就认为其是低风险，应该以该工具在特殊情境下的风险程度，即这个工具可能的最大风险程度为评估指标❌️——这种方法会造成大量不必要的摩擦，降低效率

ai答案：风险评级不绑定在工具上，而是根据“工具+参数+上下文”组合评估
- 例如对delete_file的path参数做模式匹配——`/tmp/*` 低风险自动放行，`/etc/*`、`C:\Windows\*` 高风险需人工确认
- 按可逆性分级：可逆操作低风险，不可逆操作高风险
- 批量操作、涉及金钱、生产环境提高风险等级
- 兜底：无法判定的参数组合默认按高风险处理

5. 本章的 Agent 产品表格中，所有 Agent 的动作空间都是“开放式”的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

工作流程比较固定，安全性要求高，输出内容/任务完成质量要求稳定

ai补充：合规/审计要求严格的领域（金融、医疗）

6. 人工干预机制要求 Agent 能“优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

不在线：挂起该任务并持久化当前状态

模糊的指令：**重述**用户需求，让用户判断Agent是否正确理解

7. 引言指出“好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

1. 大部分工具调用都需要自己写工具schema和调用接口，现在有的模型服务商提供内置工具，开发者从该厂商服务器动态获取工具schema即可；
2. 之前代码中需要让llm判断是否需要调用工具，现在“判断工具调用”能力已经被训练内化到模型中
